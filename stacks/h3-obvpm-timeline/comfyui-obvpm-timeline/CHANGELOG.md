# Changelog: comfyui-obvpm-timeline node pack

Changes to the nodes themselves. The workflows have their own changelog: [workflows/README.md](workflows/README.md).

Changes not yet in a release are listed under **Latest HEAD**; they become a numbered version when the pack is released.

## 0.3.1 (2026-10-05)

- Fixed: a 0.3 workflow opened while 0.2 was still running (before the update, or before ComfyUI was restarted) failed every Run after the update with "Value 1 smaller than min of 2: level_lock_frames" and "pin_state is not valid JSON ('export')". The browser kept the open tab with 0.2's six Timeline outputs while its values stayed in 0.3's order; 0.3.0 took the outputs for a 0.2 save and read the values in 0.2's order, one slot over -- and said "the settings are kept". It now also checks which order the values are in (0.2 has text at the fourth place and true/false at the sixth, 0.3 a number and text): a 0.3 save keeps its values and only loses the leftover outputs, quietly. A real 0.2 save is read back as before. A tab already opened that way and saved since keeps the shifted values: open the workflow again from its file.

## 0.3.0 (2026-10-05)

- **Changed: H3 Sampling Schedule's outputs are reordered** -- `sigmas`, `first_stage_sigmas`, `first_stage_width`, `first_stage_height`, then `dual_stage` last, so the first stage's outputs sit together. A workflow saved with the old order keeps every wire on the output of the same name: they are moved when it is opened (a node made by this version says so in its properties, `obvpm_outputs`).
- **Changed, and the reason this is 0.3.0: the Timeline has no output pins.** Its six outputs (`pin_specs`, `length`, `sequence`, `upscaling`, `hunting`, `hunt_count`) are now the fields of one bundle -- comfyui-obvpm's Bundle / Unbundle type -- which the node **sets as a constant**, named by its new first widget `set_constant` (`h3_timeline_outputs`). An Unbundle that gets that name takes the fields out anywhere in the workflow, inside subgraphs too (right-click the Timeline -> **Add Unbundle (get)**); a pasted copy gets a numbered name, and an empty name means nothing can read it. `upscaling`, `hunting`, `hunt_count` and `sequence` are still known before a Run through the Unbundle, so Mute Group If and the presets' fades work as before. **Needs comfyui-obvpm 0.2.14 or later.**
- **Changed: the node shows four rows** -- `set_constant`, `base_folder`, `crf`, `duration_seconds`. `preview_filename`, `export_filename_prefix`, `restore_groups` and `skip_restore_nodes` moved into a **⚙** settings dialog beside ✎ (also right-click -> **Timeline settings...**); the hidden settings no longer leave invisible input sockets on the node. The deprecated `auto_add` widget is gone.
- Workflows saved with 0.2 still open: the Timeline's values are read back by name (the cut, the pin, the settings), and an Unbundle placed beside it, getting its constant, takes over every wire the old outputs had -- the workflow runs as before, and a notice says what changed. When another node already sets `h3_timeline_outputs` (0.2's workflows bundled the outputs by hand under that name), the Timeline takes a numbered name.
- **Changed: the Result Preview and the Upscale Result Preview have no `path` input.** They read the save's path only by the Set node their `result_constant` names (`gen_result` / `upscale_result`); when the prompt is made the browser puts that Set node's feed in place of the name, or nothing when the save is muted for the Run. A `path` socket a saved workflow brings back is removed on load (a wire to it too, with a console note).
- New: the Timeline's player has the bar of the Result Preview under the picture instead of the browser's controls over it, so nothing shades the bottom of the frame. Its seek bar is the clip's: the whole file of the clip under the playhead, with the frames the cut plays marked by an amber line under it (in ▶ full, the built file), so what a cut leaves out is a scrub away -- paused, the picture stays on such a frame and the playhead waits at the clip's nearer end; played from there, it goes on to the next clip as the cut does. Play / pause (or a click on the picture) plays the cut as Space does, the frame buttons and a sideways scroll over the picture step along the cut (across joins and empty space), the sound button and its volume slider are remembered with the other players', and a double click or the fullscreen button shows the picture fullscreen with the bar over it. The header's ▶ quick / ▶ full still choose the mode, and its **loop** is still the sequence's.
- New, for other packs: takes of another kind that another pack keeps in a seed hunt's folder show in the Result Preview with the Run's takes and in its list of earlier generations (a node class with an `obvpm_run_takes(run_dir, prefix)` classmethod lists them; `nodes_result.run_extras`). Such a take can bring its own badges and tile actions, be marked (with its own mark texts), name what it is (`noun`: a Run of only such takes is listed as "4 drafts", say), and put buttons in the top row that act on the marked takes -- gray until one is marked; a button's route may answer with a prompt, which is queued as the Run button queues one, and the takes it acted on are unmarked. The tile buttons' plain tone is a solid dark gray.
- Fixed: in a seed hunt, the place of the next take showed the live frames of the take just finished until its own first sampling step came. It now starts empty.
- Fixed: in fullscreen, the Result Preview and the seam browser showed only the picture and its bar, so a take opened in the single view could not go back to the grid. Fullscreen now takes the whole view, top row included -- grid / single, the join modes, the list of earlier generations and the buttons beside it -- and a confirmation or seam settings dialog opened there shows inside it (it opened, unseen, behind the fullscreen picture).
- Fixed: an 8.3 ms skip in the sound at extend joins. A pin window that starts between two audio steps -- from a clip whose length is not a multiple of 3, like 124 or 362 frames, or such a cut -- is sliced from the nearest step, so the take's sound sits a third of a step off its own frames. The latents keep that (the upscale lays every clip on one audio grid and joins them exactly), but the take's MP4 now has its sound cut on its own frames, and so does the crossfade overlap; the sidecar records `audio_phase` and `audio_synced`. So a take plays in sync on its own, and its join in previews and exports no longer skips 8.3 ms (measured: 267 samples to 0). Takes saved before are corrected the same way when a preview or export is built. Two-stage runs read the first stage's pin at the same phase, so both stages hold the same sound. The held sound is now sliced from the step nearest the window's first frame in true time (the source's own phase included), so a take is never more than half a step off and nothing adds up along a chain. Previews rebuild once.
- Fixed: in the upscale, a take extended from an off-grid cut of a take that was itself off-grid could skip or repeat a whole audio step (25 ms) at its junction: each clip's sound was placed by rounding its own start. It is now placed by lineage -- its parent's first step plus the step its held sound came from -- so every junction continues the parent's sound exactly; takes saved before are placed by the same rule they were sliced with.
- Fixed: on extend joins that crossfade (guide or both mode pins, or crossfade turned on for a masked join), the last few milliseconds before the join were near-silent in the timeline preview and export and in the Result Preview's joined previews -- 3 to 30 ms depending on the overlap (7 ms for 39 frames, 26 ms for 90) -- and the take's sound in the fade ran that much early. The take's stored overlap is AAC, which decodes padded to whole 1024-sample blocks; the fade read the overlap from its end, padding first. Previews rebuild once. Masked joins without crossfade, the default, were not affected.
- Fixed: continuing a clip from its end logged "unexpected audio grid (603 steps for 362 frames); assuming no overhang" for one clip length in three (56, 107, 158, ... 362 frames). ComfyUI sizes a clip's audio to the nearest 40 Hz step, so on those lengths it ends a third of a step (8.3 ms) before the last frame; the check only expected it to end after. Nothing was wrong with the clips or the takes made from them.
- **Changed: the Result Preview's live picture has no switch any more.** The right-click **Live preview while sampling** is gone, and the picture always shows while a Run samples (to go without it, take H3 Live Preview off the model). The switch was kept in the browser per save folder, and workflows from before the Upscale Result Preview existed carried `h3_live_preview: false` on the preview they showed the upscale in: opening one turned the live picture off for the take preview of every workflow saving to that folder, with nothing on screen to say so. The stored switch is no longer read (and goes at the browser storage's next write), and the old property is ignored.
- Fixed: the Timeline's **hunt** button looked off when a workflow saved with hunting on was opened (the Run hunted all the same): it is painted from the loaded value now, as **upscale** is.
- Fixed: a double click or a drag across a node could paint the browser's blue text selection over a whole video. Videos are never text-selected now -- on the Clip Loader, the Timeline, both result previews and the seam browser, and any other video on the page (ComfyUI's own previews included). Status lines stay selectable, to copy: the takes view's, the Upscale Result Preview's, the Timeline's **next run** line, its selected clip's line and its build progress.
- New: **a very short take can be continued.** A pin's window is now taken from the source's whole stored latent: a take made by extending another clip keeps the frames it held from that clip ahead of its own (35 + 33 = 68 raw frames for a 33-frame take), so a 39-frame window ending at its end -- or at a cut close to its start -- reaches back into them, where before the take was "too short to extend". A prepend's window likewise runs on into the frames a prepend-made take led into. Those frames are the take's own latents, identical to the clip it continues there (measured: no difference at all), so the join does not move: the new take still starts at the cut, and the lineage, the seams and the upscale read it as before. The first stage of a two-stage run pins from the take's file, which holds only the delivered frames: there the frames before them are read from the file of the clip it continues, and a prepend's frames after them from the file of the clip it leads into (each found as the Result Preview finds it; refused, saying so, when that file is gone). The Result Preview's **with seams** view shows that clip from its first frame when the window reaches past it. A root clip shorter than the window is refused as before.
- New: **a prepend close to a clip's end.** A prepend's window starts at the cut and runs 39 frames on, so from a cut near the clip's end it ran past it ("cut frame 141 is outside clip_00059.mp4 (1..124 frames)"). When the next line on the timeline is a take that extends this clip, the window is now taken from that take: it stores this clip's frames up to their join, the very same latents (measured: no difference), then its own -- exactly what plays after the cut. The new take is still recorded as leading into this clip at the cut, so the timeline, the seams and the upscale place it as any prepend; its window just runs on past the clip's end, and the first stage of a two-stage run reads the same frames from the two files. Without such a take the Timeline now says how many frames are left ("a prepend at frame 102 of clip_00059.mp4 needs 39 frames from there, but only 22 are left before the clip ends") instead of naming the window's end as the cut.

## 0.2.1 (2026-10-04)

- New: seed hunting. One generation Run makes several takes from different seeds and the Result Preview shows them side by side, each labelled with its seed and its measured join; open one, add it to the timeline, and discard the rest. Turned on with the new **hunt** toggle and count (×2 to ×16) in the Timeline's header, which come out on its new `hunting` / `hunt_count` outputs. The new **H3 Seed Hunt** node makes the Run a loop: each take is sampled, decoded, saved and shown before the next starts, so the side-by-side view fills in as the Run goes -- the takes still to come hold their places, the one sampling shows the live picture there -- and a finished take can be opened while the rest sample. Only what lies between H3 Seed Hunt and the Result Preview runs again per take, so a hunt costs time, not memory. The save nodes take an optional `seed` (recorded in the sidecar) and `hunting` (the take waits in a folder of its Run, `_candidates/<run>/`, out of the clip picker, until it is added; adding it moves it out under the next free clip number). The tiles fill the panel at the takes' shape -- one row in a wide panel, a grid in a square one -- and each take's joined preview is cached, so switching between takes is instant.
- New: **browse takes** in the seam menu. Each side of a seam can open a panel with every take that fits it side by side -- the folder's takes and the seed hunts' waiting takes -- each playing joined to its neighbour; **use** puts one in the cut (a hunt's take is moved into the project folder first). The joined previews are cached, so a second look is instant. See [the widget guide](docs/h3.md#the-timeline-widget).
- New: the Result Preview and the seam browser play with a bar of their own **below** the picture -- play / pause, frame step, seek, time, a vertical volume slider, loop, fullscreen -- instead of the browser's controls drawn over the bottom of the frame. Click the picture to play or pause, double click for fullscreen (where the bar lies over the picture and slides away while the mouse rests), and scroll sideways over the picture or the bar to jog. A hunt's takes play together under one bar (play, pause and seek move them all), and every new hunt turns loop on. The live preview from KJ's Model Preview Override no longer starts over at every sampling step and can be paused, seeked and looped from the same bar.
- New: **H3 Live Preview**, the sampler's picture while it samples, in the Result Preview: each step as a short clip on the take's own timeline (every latent step held for the frames it covers, so no frame rate to set), the pinned frames at the ends included so a join can be judged while it is made, encoded as H.264 on the CPU without holding up sampling. A seed hunt's grid then runs on the latent's timeline: finished takes sit after their pinned head, in step with the live picture, and *with seams* joins each take to exactly the frames its latent pinned. It replaces KJNodes' Model Preview Override (still shown when that is what is in the graph). See [H3 Live Preview](docs/h3-nodes.md#h3-live-preview).
- Two-stage extends no longer stretch the picture at the join. The first stage's size was each side rounded to the 32 pixel grid on its own, which changes the shape for some sizes -- 960x544 at `first_stage_scale` 0.5 ran at 480x256, 6% wider than the video -- and its pins were cropped to fill that, while the latent upscale stretches the first stage back onto the video corner to corner. Everything the take made came out about 6% taller than the clip it continues, so a still background jumped at the seam, where the second stage's exact pins meet the new frames. **H3 Sampling Schedule** now picks the first stage's size on the grid in the video's shape as nearly as it allows, within 10% of the asked scale (960x544 at 0.5 runs at 512x288, 0.7% off; sizes that already halved cleanly, such as 1344x768, are unchanged), and logs the size, its scale and how far its shape is off. **H3 MCtx Pins From Pixels** squashes the pins onto the first stage whole instead of cropping them, so the upscale undoes exactly what they did; a pinned clip of another shape than the video (an imported clip) is still cropped, as the second stage crops it.
- Previews moved into a `_previews` folder inside the base folder: the timeline's full build and the Result Preview's joined take no longer sit among the clips. Old `obvpm_h3_preview` / `obvpm_h3_result` files beside the clips are no longer used and can be deleted. See [Seed hunting](docs/h3-nodes.md#seed-hunting).
- New: the Result Preview is laid out anew, its seam browser too. Along the top: **▦ grid** / **▭ single**, how much of the neighbours plays with each take -- **with seams** (joined to exactly the frames it was pinned to; the default), **with neighbours** (their parts as the cut plays them) or **result only**, remembered in this browser -- a list of the runs, the status line, and **✕ delete all** (was *discard all*) or **dismiss**. Single view shows the takes small in a row along the top and the one picked large below; a click on a take in the grid opens it there. Hover a take for **+ add to timeline**, **keep** (a hunt's take, moved into the project folder without adding it) and **✕ delete**, in its bottom right corner. Each take shows the measured join at each end it joins; in a joined mode one strip right above the bar names the parts of what plays, each over the stretch of the seek bar it plays in, the take itself as *this run*. Joined previews are built two at a time, each showing its progress over its take. In fullscreen the bar stays docked below the picture, the parts strip above it. The status line only shows brief notices that clear themselves. What a take was shown with (its lineage and measured joins) is kept on disk beside it, so an earlier hunt or a reopened workflow shows at once instead of measuring every take again. A run turns the preview to it as it starts -- a hunt's places for all its takes, the one being made marked **0:42 · SAMPLING step 3/8** (with `stage 1` / `stage 2` before the step in a two-stage run) in red -- how long it has taken, then the step (then DECODING, SAVING), showing the live picture -- and what was there comes back if the run makes nothing. The list of earlier generations brings back any Run still waiting in `_candidates`. A single generation through H3 Seed Hunt is now a hunt of one take: it waits among the candidates too (`take_01_seed_….mp4`) until it is kept or added, so nothing undecided lands in the project folder. See [H3 MCtx Result Preview](docs/h3-nodes.md#h3-mctx-result-preview).
- New: **`result_constant`** on the Result Preview (`gen_result` by default) and the Upscale Result Preview (`upscale_result`): with nothing wired to `path`, they read it from the KJNodes Set node of that name, so neither needs a wire or a Get node. A wire still wins. With comfyui-obvpm 0.2.12 or newer, the Value Presets feeding a result that only a preview reads this way (the engine settings) are no longer faded as unused.
- A seed hunt's takes are named for the hunt while they wait -- `take_01_seed_1234.mp4`, `take_02_seed_11234.mp4`, ... -- and still become the next `clip_NNNNN.mp4` of their save when kept or added. Every take's sidecar now records its save prefix (`save_prefix`).
- New node **H3 Upscale Result Preview**: wire H3 Joint VAE Decode and Save's `path` into it (or name its Set node) to play the finished upscale. It plays the rendered file itself under the same player bar as the take preview, with delete (which now also removes the `_s01`, `_s02`, ... segments of a cut with hard cuts) and dismiss, and on open shows the newest upscale. Use it instead of H3 MCtx Result Preview for upscales: on the take preview the upscale branch counted as part of every generation run, so it showed the generation sampler's live frames and an "assembling" bar from the take preview's build. The take preview still plays upscales in older workflows.
- Result Preview, fixed: the live frames from KJNodes' Model Preview Override are shown only on the preview of the branch that is sampling. A preview fed from an upscale save showed the generation's frames.
- Joined previews: a clip's part cut for one build is kept (in the clip's `_previews/_pieces`, the newest 64) and reused by the next, so the takes of a generation, which all join the same part of the same parent, no longer each decode the whole parent to cut it again -- after the first take, each joined preview takes about 0.2 s instead of about 3 s, frame for frame the same picture. Parts a seam repair changes are still cut for each take.
- Takes view playback: switching takes in single view is instant and keeps its place (the large picture draws from the take's thumbnail until its own file is loaded and placed; it never restarts the group), a picture given another file is put at the group's moment instead of its own start, pausing puts every picture on exactly the same frame, the large picture runs the clock in single view, small drift is corrected by nudging playback speed instead of seeking, and the parts strip keeps its room while a picture reloads (no flash of the pictures larger). The parts strip lines up with the seek bar at any canvas zoom.

## 0.2.0 (2026-10-02)

- H3 MCtx Result Preview: the `path` input is now optional, so a preview whose Save node is muted for a Run (a Mute Group If on the `upscaling` output, comfyui-obvpm 0.2.11 or newer) keeps what it shows instead of failing the Run. The *Switching branches* notes in [docs/h3-nodes.md](docs/h3-nodes.md#h3-mctx-timeline) now mute whole groups that way rather than only gating the samplers, so the other half's loaders never start.
- H3 Sampling Schedule: a new schedule choice, `step_range`, runs steps `from_step` to `to_step`, so one schedule can be shared out -- for example 16 steps: the first stage 1-4, the second 5-8, the upscale's refine 9-16. `extra_steps` splits a schedule's last step into more, equal ones. `refine_amount` now lives in the upscale engine settings (moved from H3 Upscale Options) and shapes the curve before any steps are cut from it. The node takes the whole settings bundle on its new `settings` input instead of a wire per field; while it is wired, the schedule comes from the bundle alone and the widgets it replaces are hidden, since changing them would do nothing (a field the bundle lacks takes its default).
- New: two-stage generation. **H3 Sampling Schedule** picks the sigmas a run samples from its engine settings: the scheduler's full schedule (exactly BasicScheduler's, so a workflow that never changes it samples as before), only its first or last x steps, or sigmas you type. With `dual_stage` on it plans two stages: the first samples the start of the schedule at a fraction of the size (`first_stage_scale`, 0.5 by default), its result is latent-upscaled to the full size, and the second stage finishes it there -- by default the first and the last 4 of 8 steps. **H3 MCtx Pins From Pixels** lets the smaller first stage continue a clip: its pins are re-encoded from the clip's frames at the first stage's size, since a latent cannot be resized. The second stage pins the clip's own latents, so the join the take is saved with is exact, as before. **H3 Second Stage Latent** joins the upscaled video with the first stage's audio and drops the first stage's mask. See [docs/h3-nodes.md](docs/h3-nodes.md#two-stage-generation).

Those frames are the take's own latents, identical to the clip it continues there (measured: no difference at all), so the join does not move: the new take still starts at the cut, and the lineage, the seams and the upscale read it as before. A pin from a take's pixels reads its file, which holds only the delivered frames: there the frames before them are read from the file of the clip it continues, and a prepend's frames after them from the file of the clip it leads into (each found as the Result Preview finds it; refused, saying so, when that file is gone). A root clip shorter than the window is refused as before.
- New: **a prepend close to a clip's end.** A prepend's window starts at the cut and runs 39 frames on, so from a cut near the clip's end it ran past it ("cut frame 141 is outside clip_00059.mp4 (1..124 frames)"). When the next line on the timeline is a take that extends this clip, the window is now taken from that take: it stores this clip's frames up to their join, the very same latents (measured: no difference), then its own -- exactly what plays after the cut. The new take is still recorded as leading into this clip at the cut, so the timeline, the seams and the upscale place it as any prepend; its window just runs on past the clip's end. Without such a take the Timeline now says how many frames are left ("a prepend at frame 102 of clip_00059.mp4 needs 39 frames from there, but only 22 are left before the clip ends") instead of naming the window's end as the cut.
- Extends, prepends and bridges: a new take now takes over one latent step earlier at its join -- 4 frames before the end of the clip it extends, or 5 frames into the clip it arrives at with a hard hold (mask ramp 0; the default soft hold already hands over later). The video decoder draws the last frames of a file with nothing after them, and the first frames with nothing before them, so the older clip's frames there never quite matched the new take, which decoded the very same latents in the middle of its own file. That was part of the fine-detail change visible at a join: measured on a 1376x768 extend, the join's detail change drops by about a third, and the rest is the model redrawing the texture, which only the upscale removes. It is just where the two clips are cut, so the quick preview, the full preview, the export and the Result Preview all show it, and nothing is re-encoded. The take records it in its recipe (`handover_edge`), so takes made before keep the join they were cut at. The upscale is unchanged: it renders the same latents either way.
- Timeline: clips joined by a green seam can now be separated. Ctrl+drag the right-hand clip to open empty space between them; both keep playing the frames they played while joined. Dragging it back flush rejoins them.
- Timeline: new **split** button in the middle of the cut row. It splits the clip under the playhead into two clips at that frame (on the snap grid while **snap cuts** is on), which can then be moved, cut or deleted separately. Both halves play the same file; nothing is re-encoded. The button is dimmed while the playhead sits on the clip's edge. The two halves join back-to-back, so an upscale treats the split as a cut.
- Timeline: extend, prepend, bridge and loop now act on the one clip you picked when the same file is in the timeline more than once (the parts of a split clip). Before, all parts showed the pin and it was unclear which one the next run would continue from. The pin row names the part (for example `clip_00033.mp4 (part 2/3)`), the pin carries that part's cut, and the new take is placed next to the part it continues from.
- Timeline: removing a clip with its ✕ now always leaves its time as empty space of the same length (merged with any beside it), so nothing after it moves, and the clips either side keep the frames they played -- before, the rest of the cut slid left to close the hole, and a clip that the removed one had continued could grow back the frames it had been cut at. A clip with nothing after it is simply removed, and so is the first clip of a looping cut. The gap's own ✕ still closes a gap.
- Result Preview: keeps nothing in the workflow any more. A finished run, adding or dismissing a take and its seam settings no longer create undo steps or change the workflow file, an undo elsewhere never brings an older result back, and a shared workflow no longer carries your last result. When a workflow opens, each preview shows this session's result, or else the newest take its Save node wrote (judged as a run would, cached per file). Dismissed takes and seam settings are remembered in this browser; settings saved in older workflows are carried over once.
- Result Preview: **dismiss** now clears the result from the preview instead of only hiding the buttons (the take stays on disk), and is offered for any result on screen, including a take already added to the timeline. A preview you cleared -- by dismissing or deleting its take -- stays empty when the workflow is opened again until a newer take exists. Before, a refresh brought up the take before the one you deleted, which read as a result you did not remember running.
- Result Preview: the upscale preview plays the rendered file itself (`upscale_00001.mp4`) instead of building a preview copy of it, so it starts at once and shows exactly the rendered pixels -- the copy was re-encoded, a second generation of the picture being judged. Only the take preview still builds `obvpm_h3_result.mp4`. The two used to share that file, rebuilt each other's preview on every look, and two builds at once failed with "The system cannot find the file specified" (`...obvpm_h3_result.mp4.tmp.mp4`). Builds of one preview file now also run one at a time, each with its own temp file, and an export copies the preview while holding that turn.
- Timeline: the parts of a split clip carry a part id in their sequence line (`[id=k3x9]`; a file that is in the cut only once never gets one), and a pin names its part by that id rather than by position. The pin now stays on its part when other parts are moved, split or deleted; a pin on a clip you split moves to the half that keeps the edge it continues from; and a pin whose own part is deleted is cleared, with the pin row saying so, instead of silently jumping to another part. The new take records its part and the cut it was queued from, so it goes back next to that part even after a reload (or next to the other half, when that part was split meanwhile and the half now owns the edge it continues from), and if that part's cut was changed while the take was generating you are asked whether to put it back (seamless) or keep yours (a cut) -- before, the cut was reset without asking and the message blamed the 17-frame grid.
- Timeline: the seam menu's list of existing takes checks where each take joins, not only which file it continues. Takes of the same file that join at another part's edge, or at a point this part's cut no longer reaches, are listed apart under *joins elsewhere*, dimmed, with their join frame. A green link whose hand cut does not meet the natural join frame now shows as a cut on the strip, matching how the upscale treats it.
- Timeline, fixed: adding a take that leads into a clip whose start is cut -- a prepend, or the right side of a bridge, which is always the case for the right half of a split clip -- left that clip starting where it was cut, so the frames between that cut and where the take hands over played twice: the join looked seamless in the Result Preview and rewound a little in the timeline. The clip now starts where the take hands over, as the clip before a take already ended where the take continues from; if you changed its start while the take was generating, you are asked.
- Timeline: clip and empty-space lengths are shown to two decimals (`2.33s`), like the total below the strip, and so are the space readouts while you drag.
- Timeline: **Space** plays and pauses the preview -- the full build when there is a current one, quick otherwise (Space never starts a build). It goes to the timeline under the mouse, else the selected one, else the only one in the workflow, and acts as the key goes down. Holding Space to pan the canvas still pans (the press toggles playback too), and Space still types in text fields.
- Timeline: after an edit (a cut, a move, a delete, the text editor) the picture shows the new cut at the playhead straight away. Before, it kept showing the old cut until the ruler was touched.
- Timeline: a **sideways wheel** over the ruler or the strip (a mouse's thumb or tilt wheel, such as on a Logitech MX Master, or Shift + wheel) moves the playhead back and forth, by half as far as you scroll, with the picture following; zoomed in, the strip scrolls along with it. A plain up/down wheel is unchanged.
- Timeline, fixed: with Nodes 2.0, the wheel over the ruler and Ctrl + wheel over the strip did not zoom (the node passed the wheel to the canvas first).
- Timeline, fixed: quick play stopped at the first empty space instead of playing through it (a gap has no clip for the info row to describe, and that error ended the playback). The info row now says "empty space" there, and pausing inside empty space holds the playhead where it is.
- Result Preview: a take's neighbours play as the timeline plays them, from where the take joins them to the other edge of their part in the timeline. A take between two parts of a long split clip used to preview with the rest of the file around it (29 s for a take that is 7.3 s in the cut). With no timeline holding the part, the whole clip plays as before.
- Load settings: a Value Presets node ([comfyui-obvpm](https://github.com/chanon/comfyui-obvpm), 0.2.14 or newer) is listed setting by setting instead of as raw widget text. Each changed value is its own row. A changed schema, and each workflow preset that differs, is one row, unticked by default, with what changed inside it (per field: type, default, `when`, tooltip; per preset: its values) behind a collapsed toggle. Loading the preset label no longer puts that preset's stored values over the take's own.
- Fixed ([#15](https://github.com/chanon/comfyui-obvpm-timeline/issues/15)): clips could show **no mctx** (and extends fell back to the pixel route, with no loop option) although their `.mctx.safetensors` was right beside them, when the browser could not read the sidecar itself. The server now answers for it, and a clip without a usable sidecar says why in its tooltip: no sidecar, a sidecar that no longer matches the video, or one that could not be read.
- Takes extended or prepended from a clip in another folder now record where that clip was, so Result Preview can show them together instead of the take alone.
- A `base_folder` typed with backslashes (`projects\my_project`) now works like `projects/my_project`. The Timeline's clip menu used to find nothing in it.
- The Timeline's upscale toggle can now be read before a run. With [comfyui-obvpm](https://github.com/chanon/comfyui-obvpm) 0.2.14 or newer, the workflow shows which engine settings the next run will use: Override Bundle Values shows their values, and the Value Presets the run will not use are faded.
- Upscaling: a timeline with hard cuts (unrelated clips, gray seams) or empty space can now be upscaled. It is split into segments that are upscaled, refined and rendered separately (`upscale_00001_s01.mp4`, `_s02`, ...) and joined into one finished `upscale_00001.mp4`, black for empty space, the sound de-clicked at the cuts. Before, such a timeline failed with "not on the latent grid", or its second shot started mid-cycle.
- Upscaling: only what the cut shows is upscaled and refined. A take trimmed to a few seconds is no longer processed whole, and the rendered file now ends where the last clip's cut says (it used to run to the end of the last take).
- Upscaling: a cut made by hand on a seamless (green) seam is now honoured as a cut. Before, the upscale silently played the natural join instead.
- The "not on the latent grid" error now names the clip and the nearest frames that would work.
- Fixed: colours of saved takes and upscales looked shifted in browsers (including the timeline preview), video players and editors -- greens duller, skin and warm tones redder. Videos are now encoded with the BT.709 colour matrix and tagged as such, like ComfyUI's own Save Video. Takes saved before this update keep playing as before, and a timeline mixing old and new takes still previews and exports correctly, only slower: such a preview or export is re-encoded as a whole instead of copied.
